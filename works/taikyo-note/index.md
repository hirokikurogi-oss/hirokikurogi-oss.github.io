# 退去ノート

賃貸の入居時と退去時の部屋を、日付つきの写真で記録する iOS アプリ。Flutter 製。企画・設計・実装から App Store への申請までを個人で担当しています。

---

## 何を解決するアプリか

退去のときに、原状回復の費用をめぐって「その傷は入居時からあったのか」が分からなくなることがあります。入居時にスマホで写真を撮っていても、あとから探せず、同じ場所と見比べられません。

このアプリは、部屋ごと・箇所ごとのチェックリストに沿って撮るだけで、どこが未撮影かが分かります。退去時には、**同じ箇所の入居時と退去時の写真**を並べて見比べられ、PDF にして管理会社へ送れます。

## 主な機能

- **撮り漏れに気づけるチェックリスト** — 玄関・リビング・キッチンなど9種類の部屋に、壁・床・天井・窓・設備・鍵の6箇所が付いた状態で始まる。撮影の進み具合は部屋ごとに表示。部屋と箇所は追加・削除・名前の変更ができる
- **連続撮影** — アプリ内カメラで撮ると、保存した時点で次の未撮影の箇所へ進む。カメラロールからの取り込みにも対応
- **入居時と退去時の比較** — 同じ箇所の2枚を、全画面のスライダーで見比べる
- **PDF の書き出し** — 入居時だけ・退去時だけの「記録版」と、2枚を並べる「比較版」。日本語と英語を選べ、1ページの写真数は2〜4枚
- **バックアップ** — 写真つきの zip を書き出し、機種変更のときに読み込める

## 設計上の判断

### 1. サーバーを持たず、端末内で完結させた

物件・部屋・写真の情報は端末内の SQLite に、写真はアプリ内のファイルに保存します。アカウント登録もサーバーも、解析 SDK も持たず、App Store のプライバシー情報は「データ収集なし」です。

入居時の室内写真は、間取りや生活の様子が写る個人的なデータです。預かる設計にしなければ、**サーバーから漏れることも、サーバーの運用コストもありません**。アプリが写真を送り出すのは、利用者が PDF や zip を自分の手で送ったときだけです。

### 2. 入居時と退去時を「箇所の ID」で対応づけた

比較ビューは、入居時と退去時で**同じ箇所**の写真を並べる必要があります。箇所の名前で突き合わせると、名前を変えたときに対応が崩れます。

そこで、箇所に固有の ID を持たせ、入居時と退去時の写真がその ID を共有する形にしました。1つの物件には入居時と退去時の記録（セッション）が1つずつあり、部屋と箇所は両方で共通です。退去時に箇所を足しても消しても、他の箇所の対応は崩れません。片方にしか写真がない箇所は、「比較なし」と表示します。

### 3. 保存時に、縮小・位置情報の削除・ハッシュ計算をまとめて行う

写真は保存時に、向きを反映して長辺2048pxへ縮小し、EXIF をすべて落とした JPEG にします。アプリの保存先には、GPS を含む位置情報を**残しません**（撮影でも取り込みでも）。EXIF の撮影日時だけは先に読み取り、アプリの撮影時刻とは別の列に持ちます（取り込みの写真は、取り込んだ時刻と元の撮影日時を分けて PDF に書くため）。

保存した JPEG の SHA-256 も記録し、写真詳細の「整合性チェック」に使っています。これは破損の検知のための値で、**改ざんを防ぐものではありません**。ハッシュも写真も同じ端末にあり、端末を操作できる人なら両方書き換えられるため、第三者への証明にはならないからです。この位置づけに合わせて、アプリ内・ストア文言・PDF のどこにも「証拠」という語は使っていません。PDF の文面にその語が入らないことは、日英ともテストで確認しています。

縮小は重い処理なので、別の Isolate で実行し、撮影の画面を止めません。

### 4. 写真のパスを相対パスで保存した

最初の実装では、写真のファイルを絶対パスで DB に保存していました。iOS はアプリを更新すると、アプリのデータ置き場（コンテナ）の場所が変わることがあり、そうなると**更新後に写真が見えなくなるおそれ**があります。リリース前のレビューで指摘され、保存するパスを保存先のルートからの相対パスに変えました。

念のため、パスを解決する関数は、絶対パスが渡されたらそのまま返します。ルートの場所を変えても相対パスから写真を読めることを、テストで確認しています。

### 5. 撮影中の操作で、保存先がずれないようにした

連続撮影では、画面上部の箇所のチップで撮影先を選びます。実機で試したところ、**保存の処理中にチップを押すと、保存先や「次の箇所」がずれる**不具合が見つかりました。

保存先はシャッターを押した時点の箇所に固定し、処理中のチップ操作は無視するようにしました。この不具合は実機でしか出なかったので、保存の処理を遅らせたテストで、処理中にチップやスキップを押しても保存先が変わらないことを確認しています。

### 6. 無料と Pro の線引きを、1つの純粋関数にした

無料で使えるのは、記録版で透かしありの PDF までです。比較版と透かしなしは Pro（買い切り¥500）です。撮影や閲覧、バックアップは無料で、**撮影を課金で止めることはしません**。

この判定は、PDF の設定を受け取って可否を返す1つの関数にして、画面側に条件を散らしていません。購入の状態は端末に保存し、オフラインでも次の起動で Pro のままになります。起動時に自動で購入の復元はしません（Apple ID のサインインを求められることがあるため）。復元は、設定画面と購入画面のボタンから行います。ストアが例外を投げたときと、購入の待ちがタイムアウトしたときは「失敗」として返します。復元がタイムアウトしたときは、保存済みの Pro 状態があれば復元済み、なければ「復元できる購入なし」として返し、どの場合も画面には例外を出しません。

### 7. バックアップの読み込みを、検査してから書く手順にした

読み込みでは、zip の中身を検査してから書き込みます。ファイル名に `..` や絶対パスがあれば（zip slip）拒否し、zip に記載された展開後サイズの合計が上限（2GB）を超えるものも断ります。manifest の版数が新しすぎる場合や、写真ファイルが欠けている場合も、DB を変えずに止めます。途中で失敗したときは、そこまでに書いたファイルを消します。

読み込んだ物件は、ID を振り直して、**常に別の物件として**追加します。既存のデータは上書きしません。同じ zip を2回読み込めば物件が2つ増え、元の物件は壊れません。zip の作成と展開は別の Isolate で行います。

### 8. PDF は1冊ずつ書き出し、容量で分ける

PDF は、ページごとに写真を1枚ずつ長辺1280pxへ縮めて載せ、全部の写真をメモリに溜めません。生成は画面を止めないよう別の Isolate で行い、1冊できるたびにその場でファイルに書きます。メールなどで送りやすいよう、目安の20MBを超えるときは、ページの区切りで複数のファイルに分けます。日本語フォントは、使う文字だけを PDF に埋め込みます。

## テスト方針

ロジック層と、実機で不具合が出た操作の流れを優先してテストしています。全体で151件です（v1.0.0 時点）。

- `image_pipeline_test.dart` — 縮小、GPS を含む EXIF の削除、向きの反映、撮影日時の読み取り、ハッシュの一致（12ケース）
- `photo_store_test.dart` — 保存とファイル削除、ルートが変わっても相対パスから読めること（7ケース）
- `backup_service_test.dart` — 書き出しと読み込みの一致、`../` と絶対パスの拒否、サイズ上限、写真の欠け（9ケース）
- `pdf_service_test.dart` — ページ分割、比較版の組み方、英日の切り替え、「証拠」の語を含まないこと（9ケース）
- `entitlement_service_test.dart` — 無料と Pro の線引き、購入・復元・キャンセル・失敗（11ケース）
- `repositories_test.dart` — 入居時と退去時が同じ箇所の ID を共有すること、削除時に関連する行が消えること（11ケース）
- `capture_flow_test.dart` — 連続撮影、処理中のチップ操作、カメラ拒否、取り込み（16ケース）

カメラ・共有・購入・ファイル選択は窓口の抽象クラスを挟み、テストでは偽物に差し替えています。
